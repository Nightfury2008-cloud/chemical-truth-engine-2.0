# Chemical Truth Engine 2.0

**Physics-Informed Integrity Verification for Chemical Cyber-Physical Systems**

> *"The computer tells us what happened; chemistry helps us check whether that
> claim makes physical sense."*

> **EDUCATIONAL SIMULATION — NO REAL CHEMICAL PROCESS IS CONTROLLED.** Unless
> you explicitly connect an ESP32 in serial mode, every number this project
> produces is generated by software. The default values are synthetic
> examples, not experimental measurements.

---

## What this project does

A normal monitoring dashboard shows readings. This prototype goes one step
further. It compares what a **controller claims** happened against what the
**sensors observed** (simulated, replayed or live), and against what **should**
have been observed if the claim were true. When the observation disagrees with
that expectation beyond a configured tolerance, the system raises an **integrity
anomaly**.

The software keeps four things strictly separate:

1. The **controller's claimed state** (what it says happened).
2. The **observed** physical measurements (what the sensors report).
3. The **expected** measurements for that claimed state (illustrative profiles
   or your configuration).
4. The **comparison result** produced by the detection engine.

Three primary results are possible:

| Status | Meaning |
|---|---|
| `NORMAL` | Every valid measurement agrees with the expected response within its tolerance. |
| `INTEGRITY ANOMALY` | At least one valid measurement deviates beyond its tolerance. |
| `INSUFFICIENT DATA` | Required information was missing, invalid or **stale**, so no conclusion was drawn. |

An anomaly is **not proof of a cyberattack**. Sensor faults, noise,
calibration errors, environmental variation, communication problems and
manipulated data can all produce the same discrepancy. The engine reports
*what* disagrees, never *why* or *who* caused it.

## What is implemented

- A **Streamlit dashboard** with five pages: Overview, Demonstration,
  Configuration, History & Charts, and Methodology & Limitations.
- A **stateful time-series simulator** (`simulation.py`): you advance the
  process **one sample at a time**; each sample depends on the previous state
  (bounded, mean-reverting process wander + small bounded sensor noise), so
  readings form coherent trends rather than unrelated random numbers. Optional
  slow sensor drift, measurement delay, and missing / invalid / stale readings
  are supported. Runs are deterministic for a given seed, and timestamps use a
  fixed simulated clock so ordinary page reruns never generate new samples.
- A **detection engine** (`detection_engine.py`) that is completely
  independent of Streamlit, with per-measurement residuals, configurable
  tolerances and data-quality / freshness checks.
- **Three data-source modes plus manual entry** (see below): simulation,
  manual input, CSV replay and optional read-only ESP32 USB serial.
- **Illustrative process profiles** (`process_profiles.py`) — the single,
  clearly marked seam where real calibration data can later replace the
  synthetic values without touching the engine or dashboard.
- **Session history** with a source column, trend charts, a run table and a
  clear/reset control.
- Interactive **expected-response configuration** (expected values and
  tolerances for each measurement).

### Measurements and units

| Measurement | Unit |
|---|---|
| pH | dimensionless |
| Conductivity | µS/cm |
| Temperature | °C |

The tolerance rule is inclusive: a measurement **passes** when
`|residual| <= tolerance` and **fails** when `|residual| > tolerance`, where
`residual = observed - expected`.

### Demonstration scenarios (simulation mode)

| # | Scenario | Expected result |
|---|---|---|
| 1 | Normal operation | `NORMAL` |
| 2 | Sensor-data inconsistency | `INTEGRITY ANOMALY` |
| 3 | Controller-claim inconsistency | `INTEGRITY ANOMALY` |
| 4 | Noisy measurements (within tolerances) | `NORMAL` |
| 5 | Stale sensor data | `INSUFFICIENT DATA` |
| 6 | Insufficient or invalid data | `INSUFFICIENT DATA` |

The *cause* of each scenario is known only because the simulator injects it
on purpose. In a real system the engine cannot infer a cause from a mismatch
alone.

## Data sources

The Demonstration page has a **Data source** selector. Every mode shows an
honesty label so it is never ambiguous where numbers came from:

| Mode | Label | What it does |
|---|---|---|
| **SIMULATION** | `SIMULATED` | Synthetic software demo. Works immediately with no hardware at all. |
| **MANUAL INPUT** | `MANUAL INPUT` | Type observed readings, expected values and tolerances into a form; the engine verifies them. |
| **CSV REPLAY** | `RECORDED` | Upload a CSV of recorded measurements and replay it row by row with full validation. |
| **ESP32 USB SERIAL** | `LIVE HARDWARE` | Optional, **read-only** serial input from hardware you explicitly connect. |

### Manual input mode

On the Demonstration page select **MANUAL INPUT**. Every numeric field starts
**empty** — nothing is pre-filled and nothing runs until you submit. The form
asks for:

- the **controller-reported state** (`TARGET REACHED / NORMAL`,
  `PROCESS IN PROGRESS`, `FAULT REPORTED` or `UNKNOWN`);
- the **observed** pH, conductivity (µS/cm) and temperature (°C) — type what
  was actually measured;
- the **expected** values for the claimed state and the **acceptable
  tolerances** — entered by you, or loaded by explicitly picking a source in
  the *"Expected values and tolerances come from:"* selector above the form:

  | Reference source | Expected values | Tolerances |
  |---|---|---|
  | *Enter expected values and tolerances myself* (default) | you type them | you type them |
  | *Configuration page values* | Configuration page | Configuration page |
  | *Illustrative profile: …* | that profile | Configuration page |

  The chosen source is shown in the result view and recorded with the run, so
  the origin of the reference values is always visible. Selecting a source
  only fills the six reference fields — your observed readings are never
  touched. A missing reference is reported as a validation error; it is never
  silently replaced with demo or Configuration values.

Click **Verify Measurements** to run one verification. All values are
validated before anything runs: pH must be 0–14, conductivity non-negative,
temperature within the app's sensor limits (−50 to 200 °C), tolerances
non-negative, and every value must be a finite number. Invalid input is
reported with a clear message and **never** verified or replaced with normal
values.

The controller-reported state is **supporting evidence only**: it is never
treated as proof that the process is normal, and a non-normal claim is never
automatically treated as an attack — only the numbers are compared. Each
successful verification is recorded in the event history with source
`MANUAL INPUT` and shown in the same structured result view as every other
mode, with a timestamp and the reference source. Manual-mode charts plot only
the values you submitted, never simulator data. Typed values are user-entered
data, not live sensor readings.

### CSV file format

Required columns (case-insensitive; extra columns are ignored):

```
timestamp,ph,conductivity,temperature
2026-01-01T12:00:00,8.01,651.2,25.4
```

- `timestamp` — ISO-8601 date/time (timezone optional, normalised internally)
- `ph` — pH, dimensionless
- `conductivity` — µS/cm
- `temperature` — °C
- optional `claimed_state` — the controller's claimed state for that row

Validation behaviour:

- missing required columns, an empty file, or a header-only file → **rejected
  with a clear error list**;
- malformed rows (non-numeric, `NaN`/`inf`, out-of-range values, bad
  timestamps) → the row is **kept** with a `missing`/`invalid` quality flag, so
  the engine reports `INSUFFICIENT DATA` — invalid data is never silently
  replaced with normal values;
- imported rows are **recorded data**: replayed and validated for structure,
  but not verified or experimentally calibrated.

### ESP32 USB serial (optional, untested on hardware)

- **Read-only by design**: the app never sends commands and never operates
  pumps, relays or dosing equipment.
- **Nothing connects automatically**: you pick a detected port and press
  Connect; pySerial ships in `requirements.txt`, and if it is ever
  missing the app reports that gracefully instead of crashing.
- Expected message format — one JSON object per line:

```json
{"ph": 8.02, "conductivity": 648.5, "temperature": 25.4, "timestamp": "2026-01-01T12:00:05", "claimed_state": "Steady operation"}
```

- Every line is validated (numbers, finite, plausible ranges); malformed
  messages are rejected and counted, never guessed at.
- A configurable **freshness limit** flags stale data: if the last valid
  sample is older than the limit, the dashboard reports staleness and the
  engine answers `INSUFFICIENT DATA`.
- **Local copies only:** a remotely hosted copy (for example on
  Streamlit Community Cloud) runs in a data centre and cannot access a
  USB-connected ESP32 on your computer — it honestly reports that no
  ports were detected. Use a local run for serial input.
- **Honesty note:** no hardware was available during development. The serial
  path is unit-tested against a *fake* serial object; live hardware reads are
  **untested** until you verify them on your own bench.

## Project structure

```
chemical-truth-engine/
    app.py                    # Streamlit dashboard (presentation only)
    detection_engine.py       # Pure comparison logic + validation

    process_profiles.py       # Illustrative expected-response profiles

    tests/
```

`app.py` contains **no detection logic**; it only renders results returned by
`detection_engine.verify(...)`. This is what lets the tests exercise the real
application logic without launching a web browser.

## Setup (Windows PowerShell)

Open **PowerShell**, move into the project folder, then run these commands one
at a time.

```powershell
cd Chemical-Truth-Engine     # or the folder where you saved the project

python -m pip install -r requirements.txt
```

pySerial (needed only for the optional ESP32 serial mode) is already
part of `requirements.txt`, so no extra install step is required.

> Tip: if `python` opens the Microsoft Store instead of Python, try `py`
> instead of `python` in every command below.

## Run the application

```powershell
python -m streamlit run app.py
```

Streamlit will print a local address, usually:

```
Local URL: http://localhost:8501
```

Open that URL in your web browser. If the port is already in use, Streamlit
automatically picks the next free one (for example `8502`) — use whatever URL
it prints.

To stop the application, return to the PowerShell window and press
`Ctrl + C`.

## Run the automated tests

From the project folder:

```powershell
python -m pytest
```

To see more detail:

```powershell
python -m pytest -v
```

The suite (245 tests) covers:

- **Detection engine** — classification, residual maths, tolerance
  boundaries, missing / `NaN` / infinite / non-numeric / out-of-range data,
  data-quality flags (`stale`/`missing`/`invalid`) and freshness limits.
- **Simulator** — reproducible sequences for the same seed, coherent changes
  across successive samples, normal/noisy readings staying within tolerance,
  anomalies outside tolerance, sensor drift, measurement delay, stale and
  missing/invalid readings, restart behaviour.
- **Manual input** — validation of typed values (missing, blank/whitespace,
  non-numeric text such as `acid`, `NaN`/infinite, pH outside 0–14, negative
  conductivity, negative
  tolerances), inclusive tolerance boundaries, residual maths and units,
  controller-claim semantics, and AppTest checks that form submissions add
  correctly sourced history records without overwriting earlier ones. The
  dashboard tests also verify that the nine manual fields are editable,
  enabled plain text inputs (regression: never `number_input` with a
  `None`/"clearable" value, which proved unreliable to type into), that
  they open empty, that empty or
  incomplete submissions are rejected without ever producing `NORMAL`,
  that missing references are never silently replaced, that the reference
  selector fills only the reference fields, that changed values and
  tolerances flip results, that per-source results and charts stay
  isolated across mode switches, and that plain reruns never fabricate
  manual runs.
- **CSV replay** — valid files, missing columns, malformed rows, empty files,
  out-of-range values, timestamps and honesty about recorded data.
- **Serial source** — message validation, malformed lines, connection failure,
  timeout handling, stale detection, and graceful behaviour without pySerial
  (no hardware required).
- **History** — repeated runs never corrupt earlier records; empty history
  never raises.
- **App render** — Streamlit's `AppTest` runs the real dashboard headlessly:
  every page, every scenario's promised status, the three data-source modes,
  configuration changes, the clear-history flow, and that plain reruns do not
  generate new samples.
- **Deployment readiness** — every third-party import is declared in
  `requirements.txt`, every source file parses with the Python 3.12
  grammar used by Streamlit Community Cloud, `.gitignore` keeps caches
  and secret files out of Git, and no absolute personal paths appear in
  the repository's user-facing files.

## Deploy on Streamlit Community Cloud

The project is ready to deploy on
[Streamlit Community Cloud](https://docs.streamlit.io/deploy/streamlit-community-cloud)
(free). The repository contains **no secrets, credentials or personal
paths**: the app needs no API keys at all, and `.gitignore` keeps
`__pycache__/`, `.pytest_cache/`, virtual environments, `.env` files and
`.streamlit/secrets.toml` out of Git.

### What works when hosted

| Mode | Hosted app | Notes |
|---|---|---|
| Simulation | Yes | fully software-generated |
| Manual input | Yes | type readings and verify them |
| CSV replay | Yes | upload a CSV from your browser |
| ESP32 USB serial | **No** | local runs only — see below |

**Why serial mode cannot work when hosted:** the deployed app executes
in Streamlit's remote Linux data centre. A USB-connected ESP32 is
physically plugged into *your* laptop, and a hosted app has no access to
it (there is no USB pass-through), so it reports "no serial ports
detected". This is a platform limitation, not a bug: the identical
serial feature keeps working in a local copy
(`python -m streamlit run app.py`). The hosted serial panel states this
openly instead of pretending hardware might appear. Everything else —
validation, detection engine, manual input, history — behaves exactly
the same online.

### Deployment steps (you perform these — nothing is pushed for you)

1. Create a new GitHub repository and upload the files above (drag and
   drop in GitHub's web UI, or push from your machine with
   `git remote add origin …` + `git push`).
2. Go to <https://share.streamlit.io>, sign in with GitHub, click
   **Create app** → "Yup, I have an app".
3. Fill in your repository, branch `main`, file path `app.py`, and pick
   an app URL (for example `your-app-name` →
   `https://your-app-name.streamlit.app`).
4. Open **Advanced settings** and choose a Python version: ideally the
   one you develop with (`3.14` if it is offered), otherwise the default
   `3.12`. Community Cloud only offers released, security-supported
   versions, and the test suite verifies every source file parses with
   the Python 3.12 grammar.
5. Click **Deploy**. The first build installs `requirements.txt` and
   takes a few minutes.

### Updating the deployed app

- Edit files in GitHub and commit to the main branch — Community Cloud
  rebuilds automatically (the platform enables `runOnSave`).
- Changes to `requirements.txt` take a few extra minutes to install.
- This app needs **no secrets**; never add credentials to the repository
  (`.streamlit/secrets.toml` is git-ignored if you ever need it).

### Hosted-app limitations

- **Public URL:** anyone with the link can use the app. There is no
  login — keep the app free of private data (it holds none by design).
- **History is per browser session** and disappears on refresh, restart
  or app sleep — exactly as when running locally.
- The app may be put to sleep after long inactivity; opening its URL
  wakes it.
- Serial mode is unavailable (above). Simulation, manual input and CSV
  replay are fully usable online.

## A short guided demonstration

**Normal operation**

1. Start the app (see above) and click **Demonstration** in the sidebar.
2. Leave the data source on **SIMULATION** and choose **1. Normal operation**.
3. Click **Advance one sample** a few times. The status card shows **NORMAL**;
   every row of the comparison table is `PASS`, and the residuals sit inside
   their tolerances. The trend chart fills in one point per sample, and the
   sidebar counter shows how many runs are recorded.

**Noisy readings (still within tolerance)**

4. Choose **4. Noisy measurements (within tolerances)** and advance a few
   samples. The readings visibly wobble but the result stays **NORMAL** —
   noise inside the tolerance is not an alert.

**An anomaly**

5. Choose **2. Sensor-data inconsistency** and advance. The status changes to
   **INTEGRITY ANOMALY**; the pH row shows `FAIL` and the reasons name the
   measurement and by how much it exceeded its tolerance. Read the reminder:
   this is a discrepancy, not proof of an attack.
6. Choose **3. Controller-claim inconsistency** — the controller claims
   "Target state reached" while the process is still steady. The expected
   response comes from the target-state profile and the readings disagree
   with it.

**Stale / invalid data**

7. Choose **5. Stale sensor data**: the frozen pH reading is flagged `STALE`
   and the result is **INSUFFICIENT DATA**.
8. Choose **6. Insufficient or invalid data**: missing pH and `NaN`
   conductivity yield **INSUFFICIENT DATA** — never `NORMAL`, and not
   automatically an attack.

**Configuration effects**

9. Open **Configuration**, change the **pH tolerance** to a very small value,
   click **Apply configuration**, then re-run scenario 1. A narrower tolerance
   can turn a previously normal result into an anomaly — this shows the
   trade-off between sensitivity and false alarms.

**Manual entry**

10. On the Demonstration page select **MANUAL INPUT**. All nine fields open
    empty — choose **Configuration page values** in the reference selector
    to fill the six reference fields, then type the observed values
    `8.0 / 650.0 / 25.5` and click **Verify Measurements** — you get
    `NORMAL` (residuals are zero). Now change *Observed pH* to `9.5` and
    submit again: the pH residual of `+1.5` exceeds the `±0.5` tolerance,
    so the result becomes `INTEGRITY ANOMALY` — a contradiction with the
    "target reached" claim. Widen the pH tolerance to `2.0` and submit once
    more: the same reading now passes, showing how tolerance changes the
    outcome. Submitting with any field empty is rejected outright — missing
    data is never treated as a pass.

**CSV replay**

11. On the Demonstration page select **CSV REPLAY**, upload a CSV with the
    columns `timestamp,ph,conductivity,temperature`, then click **Replay next
    sample** row by row. Try a file with a bad value (for example `abc` in the
    pH column) and observe the validation list plus the `INSUFFICIENT DATA`
    result instead of a silent pass.

**History**

12. Open **History & Charts** to see the trend of observed versus expected
    values, the table of previous results (including each run's **Source**),
    and **Clear demo history** to reset.

History is stored only in your browser session (`st.session_state`). It is
**temporary** and disappears when you close the tab or restart Streamlit. It
is never written to disk or sent anywhere. **Restart simulation** resets the
simulator (same seed → identical sequence) but keeps the event history.

## Configuration and its limits

The default expected values and tolerances are **synthetic software-demo
defaults only**:

| Measurement | Default expected | Default tolerance |
|---|---|---|
| pH | 8.0 | ±0.5 |
| Conductivity | 650 µS/cm | ±80 µS/cm |
| Temperature | 25.5 °C | ±2.0 °C |

They are **not** scientifically calibrated, not measured in a laboratory, not
validated for any real process and not universally valid.

A real implementation would require **experimental calibration under defined
process conditions**, repeated across operating points, with the **measurement
uncertainty** of each instrument accounted for. Note also that pH must never
be assumed to vary linearly with chemical dose — no such reaction model is
implemented or claimed to be verified in this prototype. The process profiles
in `process_profiles.py` are invented demonstration numbers; replacing them
with calibrated data requires no other changes.

## Safety and privacy

This project is a software-only simulation. It deliberately does **not**:

- control or drive any physical equipment;
- send commands to hardware (the one hardware path, USB serial, is strictly
  read-only and never connects automatically);
- perform any chemical experiment;
- scan networks or include any offensive-security functionality;
- send readings to third parties or require API keys / cloud credentials;
- collect personal information, read environment secrets or add telemetry.

The published repository contains no absolute personal paths (checked by
the test suite), and `.gitignore` excludes secrets
(`.streamlit/secrets.toml`, `.env`), virtual environments, caches and
test-generated files from Git.

It makes no claim to detect all attacks, and no claim of industrial
compliance or certification. Any future physical testing should be supervised
and kept separate from this software-only simulator.

---

## Limitations

- **Not industrial-ready.** There is no calibration study, uncertainty budget,
  safety analysis, authentication, auditing or access control.
- **Session-only history.** Records live in browser memory and are lost on
  refresh or restart.
- **Synthetic data only.** No real measurements or attack data have been used,
  so no performance claims are made.
- **Serial untested on hardware.** The serial integration was developed and
  tested with a fake serial object only.
- **No serial when hosted.** A deployed copy (e.g. Streamlit Community
  Cloud) cannot reach USB hardware on your computer — serial mode is for
  local runs only.
- **Public when hosted.** The default Community Cloud URL has no login;
  anyone with the link can use the demo app (it stores no private data).
- The expected response is a simple per-state expected value (from an
  illustrative profile or your configuration), not a full chemical process
  model. Real chemistry is far more complex.

## Troubleshooting

| Problem | What to try |
|---|---|
| `python` opens the Microsoft Store | Use `py` instead of `python` in every command. |
| `ModuleNotFoundError` | Make sure you ran `python -m pip install -r requirements.txt`, and that you start the app from inside the project folder. |
| `Permission denied` / file in use | Close the running Streamlit window or press `Ctrl + C`, then retry. |
| Port already in use | Streamlit will pick the next free port automatically — use the URL it prints, or force one with `python -m streamlit run app.py --server.port 8502`. |
| Browser shows a blank page | Confirm the PowerShell window still shows the app running and that you opened the exact `Local URL` it printed. |
| `pytest` not found | Run tests as `python -m pytest` (this guarantees the correct Python is used). |
| Serial mode says pySerial is missing | Install it with `python -m pip install pyserial` — simulation and CSV replay keep working without it. |
| Serial mode shows "No serial ports detected" | Check the USB cable/driver, then press **Refresh ports**. |
| Hosted app shows "No serial ports detected" | Expected: a remotely hosted app cannot see USB devices on your computer. Use a local copy for serial mode — simulation, manual input and CSV replay work online. |
| CSV upload reports missing columns | Your header must contain `timestamp`, `ph`, `conductivity`, `temperature` (case-insensitive). |
| Corporate proxy / offline install | Dependencies must already be present in your Python environment; otherwise install them from a machine with internet access. |
